# Fabric Schedule Visibility

A read-only view of Fabric workload schedules and concurrency. Operational metadata
only; no patient data. Milestones 0-3 supply the authenticated application,
data model, scheduling calculations, and deterministic sample-data experience.
Milestone 4 includes owner-scoped Live discovery and read-only schedule/history
collection. The initial empty-source scope was expanded with user approval.

- Fabric Apps tenant setting enabled, and a capacity-backed workspace with

## Milestone 4: owner-scoped Live collection

The approved source scope is **all capacities and workspaces the app owner can
access**. POC-Scheduler is the approved deployment target, not a source allowlist.
The user explicitly selected an owner-only pilot rather than per-viewer delegated
source access, and approved publishing to POC-Scheduler after validation.

- The Functions workspace is `packages/functions`. All Rayfin packages and the
  Functions worker stay pinned to **1.36.2**. Types are generated by the documented
  development watcher, never edited manually.
- Admin's approved **Demo / Live** selector separates data sources and resets
  shared filters. The header badge changes with the source. Demo remains the
  default on reload; switching modes does not delete or overwrite records.
- Live exposes a single-select source capacity, multi-select source workspaces
  (empty means all discovered workspaces), **Sync now**, actionable failures,
  and the latest 20 persisted `SyncRun` results. Source capacity selection does
  not change any workspace's capacity assignment.
- The shared Capacity filter defaults Timeline's size reference, summary card,
  and footer to the selected capacity's discovered F SKU. All capacities sums
  known capacity units and each capacity's published refresh limit separately;
  it does not treat the capacities as a pooled SKU. Unknown/nonstandard sizes
  are excluded from totals; no known size displays Unavailable without a
  threshold line. A manual Timeline override lasts until the capacity or source
  changes (or refreshed capacity metadata changes). Demo defaults use its capacity
  metadata in the same way.
- `getLiveWorkspaces` paginates `/workspaces` and `/capacities`. The capacities
  endpoint lists capacity administrators/contributors; a workspace can be
  accessible even when its capacity metadata is not. Such workspaces remain
  available when selecting all sources and their actual capacity IDs are kept.
- Every outbound source request is GET, with encoded continuation tokens,
  fixed Fabric origin, rejected redirects, and bounded 429 `Retry-After` delays.
  Reads are sequential (below the five-call limit), have individual 15-second
  deadlines, and share a 60-second budget.
- Sync processes one workspace and at most two job-capable items per invocation.
  The frontend follows continuations before moving to the next workspace.
  `SyncRun` remains Running between batches, then becomes Succeeded, Partial,
  or Failed. Completed writes are durable and repeated syncs upsert deterministic
  item/run IDs without touching annotations or demo records.
- Daily, Weekly, and anchored minute-interval schedules preserve time zones,
  start/end bounds, disabled schedules, and multiple schedules for one job.
  Windows time zones map through Unicode CLDR's global (`001`) mapping.
  Duplicate starts are not double counted. Monthly/unrecognized schedules and
  schedules exceeding the 4000-character metadata limit are explicitly skipped
  with Partial sync results rather than approximated.
- Recent retained job instances drive average, median, p90, failure totals, and
  latest status. Fabric limits retained history (often the most recent 100
  completed runs), so a sync cannot guarantee complete seven-day history for
  high-frequency jobs. Failure bodies are not copied from source systems.
- Removed or unsupported items lose their projections; the app never changes
  source items, schedules, capacity assignments, or job execution.
- The installed version supports only the built-in audiences; it cannot declare
  the Power BI resource audience. Semantic models and Gen1 dataflows are skipped
  and reported; those require the optional Milestone 5 collector.
- Refresh/auto-refresh polls only imported items whose projected execution
  overlaps now +/-15 minutes, plus items last seen InProgress. Requests contain
  at most 20 item keys. Live actuals use verified run starts, never the demo
  generator; unmatched scheduled starts are shown explicitly as unmatched.

The centralized job-type map is in `packages/functions/src/normalize.ts`.
Its sources are the documented
[pipeline](https://learn.microsoft.com/fabric/data-factory/pipeline-rest-api-capabilities),
[notebook](https://learn.microsoft.com/fabric/data-engineering/notebook-public-api),
[Spark job](https://learn.microsoft.com/rest/api/fabric/sparkjobdefinition/background-jobs/run-on-demand-spark-job-definition),
[Dataflow Gen2](https://learn.microsoft.com/fabric/data-factory/dataflow-gen2-public-apis),
and [Copy job](https://learn.microsoft.com/rest/api/fabric/copyjob/background-jobs/list-execute-schedules)
APIs. Unsupported item types are not probed with invented job types.

### Identity and validation

`services.functions.auth.type` is `application`. Deployed external calls use the
app item's owner identity, not the invoking user's identity. Give that identity
the documented read permissions on source workspaces and items and
Capacity.Read.All for capacity metadata. Audience declarations do not grant
workspace access. App-owned writes use the caller's Rayfin token.
The verified owner subject in `packages/shared/src/access.ts` is enforced by
database policies on all five entities, the authenticated UI gate, and a
server-side invocation-subject check before external reads. The Functions
gateway authenticates the invocation token; the subject check adds authorization,
not a replacement token-validation mechanism. Managed-host `/users/{id}` subjects
are normalized like the SDK's session user ID; malformed or non-owner subjects
remain denied. Tokens stay in the host.
Before sharing this app or transferring ownership, redesign/reconfigure these
boundaries; do not broaden them to every authenticated user.
Local Functions resource connections use the account selected by Azure Functions
Core Tools, independently of CLI-backed browser sign-in.

For isolated tooling on a machine whose global Node version is unsupported:

```powershell
npm exec --yes --package=node@24 --package=azure-functions-core-tools@4 -- rayfin dev functions apply --no-debug
```

The local Functions host requires interactive resource authentication. Do not
replace a failed local token binding with frontend tokens, alternate caches,
or a silent remote fallback. Production uses the deployed application identity.
`npm run test:functions` exercises owner authorization, safe reads, normalization,
resumable batching, idempotent persistence, and partial outcomes.

## Data model

`rayfin/data/schema.ts` registers `ScheduledItem`, `RunInstance`, `ItemAnnotation`,
`SavedView`, and `SyncRun`. The template's generic starter entity is not registered.
The exported `AppSchema` and shared client contracts cover the same five entities.
Every nullable field declares both `?` and `{ optional: true }`; all text fields
have explicit MSSQL lengths.

- `ScheduledItem.itemKey` is unique and represents `workspaceId:itemId:jobType`.
  `ItemAnnotation.itemKey` is also unique. Run history is one row per run, so
  `RunInstance.itemKey` is intentionally not unique.
- `SavedView` grants authenticated CRUD only when `claims.sub` equals `user_id`.
  Policies validate ownership but do not stamp it: when creating a view, set
  `user_id` from the authenticated session's `user.id` (the subject), never from
  editable form input. Fail if no authenticated user is available.
- All five entities additionally require the configured owner subject for every
  action. These permissions apply to app metadata, not to source Fabric workloads.
- Schedule strings use comma-separated `Mon`–`Sun` and `HH:mm` values, with
  at most 100 time slots. Time zones are IANA IDs. `Monthly` is stored, but
  occurrence expansion in Milestone 2 covers Daily, Weekly, and Interval only.
- Lists must select explicit fields and page with
  `.first(n).executePaginated()` and `.after(endCursor)` until `hasNextPage` is
  false. Use the accumulated `results.length`, not `count()` or `totalCount`.
  Grouped aggregations cannot use `.select()` or `.orderBy()`; sort the result
  in TypeScript.

Restart `npm run dev` after schema changes to apply them to the approved backend.
`npm run test:data` checks the generated MSSQL configuration and ownership policy;
it runs automatically as part of `npm test`.

## Scheduling calculations

The pure TypeScript API is exported from `packages/frontend/src/domain/index.ts`.
It does not call Fabric, read the current clock, access browser storage, or mutate
its input. All occurrence and result windows use UTC epoch milliseconds
(`startMs`, `endMs`), with half-open overlap semantics `[start, end)`: a job
ending when another starts does not overlap it. Zero-duration occurrences remain
visible as scheduled instants but do not contribute to concurrency.

### Occurrence expansion

`expandOccurrences(items, date, displayTz?, metric?)`

- `date` is a strict `YYYY-MM-DD` calendar date in `displayTz` (default
  `America/New_York`), not a date inferred from the machine's time zone.
  `metric` is `average` (default) or `median`; each falls back to the other.
- `ScheduleDefinition` accepts nullable optional schedule/history fields from
  the data API. Required fields must already have been normalized (notably
  wire booleans) before calling the domain layer.
- Daily and Weekly schedules use comma-separated `HH:mm` clock times in the
  item's IANA zone, with at most 100 slots. Duplicate times are emitted once.
  Weekly requires `scheduleDays`; when supplied for Daily or Interval, those
  days restrict them too. Weekdays are always evaluated in the item's zone.
- Missing spring-forward clock times are skipped. A repeated fall-back clock
  time is emitted once at its earlier UTC offset. Duration is elapsed time,
  even across a clock change.
- Interval schedules start at item-local midnight, repeat every
  `intervalMinutes` of elapsed time, and reset at the next local midnight.
  An hourly interval therefore has 23/25 starts on spring/fall transition days;
  unlike fixed clock schedules, elapsed intervals can visit the repeated hour
  twice. `scheduleTimes` does not anchor intervals.
- Durations fall back to five minutes with `noHistory: true` when neither
  average nor median exists. Known zero duration is not missing history.
- Includes every occurrence overlapping the display day, including starts on
  earlier source-calendar days. Start and end are not clipped to midnight.
  Disabled items are omitted. Enabled Monthly schedules throw an explicit
  unsupported-schedule error rather than disappearing silently.

### Concurrency and overlap

`overlapping(occurrences, sliceStart, sliceEnd)` returns the original occurrences
intersecting a UTC window.

`computeConcurrency(occurrences, sliceMinutes = 5, window?)` returns slices with
separate `projected` and `actual` counts. Each has `total` and `byType`. A slice
records the **exact simultaneous peak**, not the number of jobs touching any
part of the slice; `byType` is the composition at the earliest total peak, so
stacking it does not invent concurrency. It is not each type's independent
maximum. To check a type-specific limit (such as 160 semantic model refreshes),
compute concurrency for that type's occurrences separately.

Supply `displayDayWindow(date, displayTz?)` as `window` for a full day including
zero-count slices (276/300 five-minute slices on spring/fall transition days).
Without a window, bounds cover the occurrences, rounded to UTC slice boundaries;
an empty input produces no slices. `peakConcurrency` exposes the same exact
window calculation used by the strip and slot finder. Actual occurrences must
be supplied explicitly with `kind: 'actual'` and observed bounds; projected
and actual series are not added together or deduplicated implicitly.

### Slot finder

`findSlots(occurrences, durationMin, windowStart, windowEnd, days, displayTz?)`

The explicit occurrences argument supplies the missing schedule context from
the original four-argument sketch without hidden state. `days` is a list of ISO
calendar dates; duplicates are ignored. Window bounds are `HH:mm` clock times
in the display zone. End at/before start means a window ending the next day
(equal bounds mean 24 hours).

Searches every five clock minutes starting at the window start, returns up to
three full-duration suggestions, and ranks by exact peak across all supplied
occurrences and item types, then earliest UTC start. It never schedules or moves
a Fabric job. Pass only projected occurrences when ranking projected load;
pass actual occurrences separately if evaluating observed load.

Suggestions may overlap each other: they are alternative start times, not
three reservations. Missing spring candidate times are skipped; repeated fall
candidate times use the earlier offset. A nonexistent window-end clock time
throws an explicit error. Invalid dates, zones, schedule values, negative
durations, and malformed time ranges are surfaced as errors.

## Sample demo and user interface

1. Start the app using the Development commands and sign in.
2. Open **Admin**, select **Load sample data**, and wait for the progress bar
   to finish. All creates use authenticated `client.data` calls with at most
   ten concurrent requests. A failed operation is reported; press Refresh to
   inspect partial results and load again to resume. Re-loading does not
   overwrite existing annotations. Initial loading can take several minutes;
   keep the page open and avoid restarting the dev server or running a build
   during loading (the build rewrites the development environment file).
3. Set **Schedule date** to November 16, 2026 and choose **Timeline**. At 06:00,
   180 projected semantic refreshes exceed the 160 reference line. Normal
   Tuesday-Friday semantic peaks are 130. The blue semantic-only line is
   separate from the stacked all-type peak composition.
   **Today** selects the current date in the selected display time zone.
   The **Display time zone** dropdown uses common regional groupings (Eastern,
   Central, Pacific, etc.) backed by IANA zones, plus UTC. Regions with different
   daylight-saving rules remain separate; seasonal offsets update automatically.
   Changing it updates displayed times without changing source schedules.
4. Select **SemanticModel** in **Item types**, then click a concurrency strip bar or
   choose the accessible **Concurrency slice** selector to focus the Gantt.
   Select **All occurrences** to clear the slice. Zoom supports 24h / 4h / 1h,
   with x-axis and vertical Gantt dataZoom sliders. Zoom is a 24h / 4h / 1h
   segmented button group. The lower Gantt has item/type row labels, Executive
   annotations, alternating row guides, a time-zone-labeled start axis, and
   projected duration labels where space permits. The right slider pages
   through 14 visible items; narrow screens can scroll the chart horizontally.
   The Gantt shows projected schedules only, using the same item-type colors
   as the concurrency chart, without actual durations or success/failure states.
   Both horizontal time sliders synchronize the two charts in either direction;
   the 24h / 4h / 1h buttons also update both. The vertical slider only scrolls
   Gantt items. Hover for full item names, criticality, owner, and projected
   duration. The Now line is
   shown only when the current instant falls within the selected display day.
5. Inspect the 08:50 slice for the Cardiology/Radiology collision. Click a
   Gantt bar or Schedule row for the last five runs and editable criticality,
   business owner, and notes. Annotation changes affect this app only.
6. Open **Slot finder** to compare three lower-congestion alternatives using
   weekday recurrence checkboxes (all seven selected by default), duration,
   and a time window. Each option is one common local start time across every
   selected weekday in the week containing the schedule date. Ranking minimizes
   the worst daily peak, then average daily peak, then start time; counts exclude
   the proposed job. Item filters apply, but shared day/time filters do not hide
   competing schedules. Click an option's peak count to expand or collapse
   the jobs simultaneous at each day's first exact peak (not all jobs that
   overlap the window). Overnight searches include the following day's workload;
   nonexistent DST starts are excluded unless valid on every selected day.
   Future weeks can differ. Suggestions never move or edit Fabric schedules.
7. Use **Today**, then **Running now**, to view simulated starts, elapsed vs.
   average duration, and >1.5x overruns. Refresh re-jitters simulation, and
   auto-refresh repeats every 60 seconds. Today's Timeline overlays these
   actual-shaped sample starts in the upper concurrency chart only; they are
   not live observations.
   Running now has column headers with info popovers for item/workspace,
   start times, elapsed/expected duration, and duration status. Expected duration
   falls back from average to median to five minutes. "Running longer than
   expected" means strictly more than 150% of that duration, not a failed run.
   Schedule and Running now rows have left-edge item-type stripes using the
   Timeline palette. Hover or keyboard-focus a stripe to see the full legend
   and the current row's type. Type colors do not indicate run health;
   failed Schedule rows retain their red background.

The sample generator uses a seeded RNG, fixed UUID namespace, 12 fictional
workspaces, 385 items (300 semantic models, 40 Dataflows Gen2, 25 pipelines,

week, not today's rolling seven days. Failure rates are approximately 5% Monday,
2% weekends, and 3% other weekdays. Refresh durations are predominantly
log-normal at 1-8 minutes; lakehouse jobs run 30-60 minutes. Missing histories
retain the five-minute projection flag.

Running simulation uses occurrences overlapping the current time and up to two
earlier interval-schedule occurrences as deliberate overruns. These use genuine
schedule slots from today or yesterday; each item appears at most once.
Execution starts at or after its planned time, with up to 30 seconds of delay,
never in the future. Earlier occurrences are selected only within a bounded
window (three expected durations or two hours, whichever is longer), rather
than inventing schedule times or week-long runs. Running now displays dates
alongside start times to make overnight runs unambiguous.
The header's **Sample** badge identifies the data source; Running now never writes synthetic in-progress
runs back to the database. Schedule date applies to Schedule/Timeline; Running
now always uses the actual current date, labeled above its results.

The four summary cards have info buttons explaining their calculations, filter
scope, and date context. Only the header badge labels the data as Sample;
other views, help, and captions omit repeated source labels. Capacity references
follow the selected Timeline SKU. The failure card derives its date range from
loaded runs for the filtered items in the display time zone, or shows
**No recorded history**; changing the schedule date does not shift stored history.

## Original template reference

> **⚠️ This repository is under active development.** Features and instructions may change.

This is the workspace template the Rayfin Copilot plugin uses to build Fabric Apps.
The base is small on purpose: dynamic authentication, theming, an error boundary, and a welcome page that works inside or outside the Fabric portal after sign-in.
Capabilities such as Power BI analytics and trusted server-side functions are added on demand with `npm run pack:add -- <pack>`.

## Workspace layout

The application is an npm workspace with one control root and three base packages:

```text
.
├── package.json                 # Root commands, workspace members, and applied packs
├── rayfin/
│   └── rayfin.yml               # Rayfin services and package paths
├── packages/
│   ├── frontend/                # React, Vite, UI, and static output
│   ├── data/                    # Entity registration and data schema exports
│   └── shared/                  # Isomorphic contracts shared across runtimes
└── scripts/                     # Capability-pack tooling and template checks
```

The packages have stable internal names: `@rayfin-app/frontend`, `@rayfin-app/data`, and `@rayfin-app/shared`.
Scaffolding personalizes only the root package name; it does not rename member packages, local dependency keys, or import specifiers.
The root coordinates the workspace but is not another application package.

The base does not include `packages/functions`.
That package is created only when the functions capability is applied.

## The starting view

`packages/frontend/src/App.tsx` starts on an illustrated blueprint of the pieces a Fabric App can grow into.
The blueprint and live source activity ship in every scaffold.
The optional Finley mascot is off by default.
Default scaffolds contain no companion code, styles, or tests.
Replace `<EmptyStatePreview />` in `App.tsx` with your own view when you start building.
The welcome page is app content and requires an authenticated session.
The app defaults to light regardless of the operating-system theme, while explicit host appearance and user theme choices remain supported.

### Replacing the welcome

Replace the `EmptyStatePreview` import and render in `packages/frontend/src/App.tsx` with your app.

Run typecheck, build, and tests after cleanup so no dangling imports remain.

## Capability packs

Apply a capability before customizing the app:

```sh
npm run pack:add -- analytics
npm run pack:add -- functions
```

Packs install dependencies with one root npm workspace install.
They do not create nested lockfiles or a separate nested installation.

The functions pack creates `packages/functions` as `@rayfin-app/functions`, enables the service at that path, and wires its generated schema into the frontend client.
It composes the functions build into the root build, Fabric build, and type-check commands.
Reapplying the pack preserves authored files.

If an install fails, the runner rolls back pack-owned file changes and reports any concurrent edits it cannot safely restore.
It preserves the install error and leaves the pack retryable.
Installed dependencies and installer-written lockfiles are not rolled back.
Follow the [failure recovery guidance](scripts/pack-manifest.md#failure-recovery) before continuing.

Template tests validate the pack structure and wiring.
With app dependencies installed, they also check the starter and analytics seed against the generated frontend lint rules.
They do not validate deployed secrets, app-identity permissions, downstream endpoints, or the maximum duration supported by the hosted functions path.

## Distribution and repository validation

The CLI and VS Code display this workspace as **✨ Use default template**, using the existing `blankapp` template ID.
Its canonical `universal-app` name remains hidden to avoid a duplicate listing, but it stays selectable explicitly for plugin automation.

Inside the Project Rayfin repository, the parent `samples/universal-app/` directory is a contributor-only Rush validation harness.
The harness generates an ephemeral `target/`, replaces published Rayfin ranges only in that target with repository-local package links, installs it, and runs the root validation commands.
The outer harness, local links, generated target, and target install output are not part of a generated app.
The committed inner template keeps published Rayfin ranges and uses `*` for local workspace members, so it remains distributable without repository-relative dependencies.

## Instructions for building a new web app

1. **Open the generated app**: Open a terminal in the project created by the Rayfin CLI, VS Code, or the Rayfin Copilot plugin.
2. **Install dependencies if needed**: Run `npm install` from the workspace root.
3. **Build the app**: Use your preferred editor or coding agent.
   If you use GitHub Copilot CLI, run `copilot`, then describe what you want to build.
   If the app should read an existing Power BI semantic model, include its name or dataset ID.
   If it should own its own records, or you want a mock-up, say so instead.
4. **Deploy it**: Ask Copilot to deploy, or run `npm run rayfin:up`, then open the Fabric URL it returns.
   Both the direct static-hosting URL and the Fabric portal URL support authenticated use.
   App content remains protected until sign-in succeeds.
